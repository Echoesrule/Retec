# RETEC Architecture Audit — Vercel, Render & Flask Homepage Cold Start

## 1. Executive Verdict

**Verified state:** The repository is a single Flask application. `vercel.json` rewrites *all* requests (`/(.*)`) to `https://retec.onrender.com/$1` with no build step, no static export, and no Python runtime defined on Vercel. Render runs the Flask app (`gunicorn app:app`, per README). The homepage is fully server-rendered by Flask (Jinja2). The public frontend is *not* independently hosted on Vercel; Vercel acts purely as a reverse proxy to Render.

**Answer to the core question:** The initial HTML for `/` is generated by Render (Flask). If Render is asleep, the first request that reaches Render must wake it; the proxy does not eliminate the cold start. The page is not hidden behind a global loader *waiting for additional API calls* in a way that masks a sleeping backend — the HTML itself is what arrives from the backend.

## 2. Verified Deployment Flow (Mermaid)

```mermaid
flowchart TD
  U[Visitor Browser] --> V[Vercel (proxy)]
  V -->|vercel.json rewrite: /(.*) -> https://retec.onrender.com/$1| R[Render Web Service]
  R -->|gunicorn app:app| F[Flask app: app.py]
  F -->|Jinja2 render| T[templates/index.html + base.html]
  F -->|SQLAlchemy| DB[(Supabase/Postgres or SQLite)]
  F -->|HTTP (threaded/off-thread)| EXT[External APIs: GitHub, ip-api.com, Brevo, etc]
  R -->|static files via Flask or CDN path| U
```

**Verification (exact evidence):**
- `vercel.json`: rewrites all paths to Render (line 1-9).
- `README.md`: Render start command `gunicorn app:app` (line ~45); Vercel not mentioned as hosting static frontend.
- `app.py`: single app entrypoint; models/routes/templates in same repo.
- `.github/workflows/keep-warm.yml`: pings `https://retec.onrender.com/healthz` every 5 min to prevent Render sleep (explicit comment acknowledging Render sleep/cold start and Vercel proxying to Render).

## 4. Homepage Critical Path

**What blocks the initial HTML response (server-side):**
- `home()` calls `get_homepage_data()` synchronously:
  - `get_projects()`: DB query `Project.query.filter_by(visible=True)...all()` (line ~1871-1876). If result non-empty → returns DB data (no network). If empty table → may call `get_github_projects()` which does blocking HTTP GET to `api.github.com` with timeout 5s (lines ~1842-1867).
  - `Testimonial.query.filter_by(active=True).order_by(Testimonial.sort_order).all()` (line ~3286)
  - `JournalArticle.query.filter_by(status='published').order_by(...).limit(3).all()` (lines ~3287-3288)
- `inject_globals()` (context processor) runs before rendering: two DB queries (`FunFact`, `SiteSetting`) synchronously (lines ~2915-2925). Also builds `meta_url` etc (no blocking I/O except maybe not present).
- `render_template('index.html', ..., form=ContactForm(), **get_homepage_data())` returns rendered HTML.

**What does NOT block initial HTML (server-side):**
- `track_pageview` spawns daemon thread (line ~3116-3137) — returns immediately.
- `journal_scheduler_hook` may spawn daemon thread or return (lines ~3166-3180, calls `journal_scheduler_tick` which uses lock/spawns thread when due).
- `record_visitor_location` spawns thread after pageview insert in worker (non-blocking).
- Geolocation (`lookup_location`) does HTTP to `ip-api.com` with timeout 2s but only from threads (lines ~1660-1710).

**Frontend (blocks perception, not HTML):** Motion/loader stack initializes after HTML parse (core.js/loader.js). The global loader is a UI mechanism; if backend is asleep, HTML itself is delayed until Render responds.

## 5. Vercel Feasibility

**Current state:** `vercel.json` is a pure proxy. No `api/` Python functions, no static build output configured for Vercel to serve. Vercel is not executing Flask.

**Can we serve frontend independently on Vercel?**
- Feasible in principle if we pre-render `index.html` (and other truly static public pages) and host them as static assets on Vercel, while keeping Flask backend on Render for APIs, admin, forms, sessions, CSRF, DB access.
- **Constraints from codebase:**
  - `index.html` extends `base.html` and expects server context: `fun_facts`, `meta_*`, `hero_*`, `css_version`, `get_image_url`, `cube_positioner_enabled` (session-dependent), plus data passed from `home()` (`projects`, `testimonials`, `blog_posts`, `services`, `process`, `project_types`, `budget_options`, `form`). 
  - Form rendering uses Flask-WTF/CSRF context (forms embedded in templates; CSRF tokens injected via WTForms/Flask-WTF). 
  - `base.html` likely includes CSRF meta tag or form handling tied to Flask session/CSRFProtect.
  - `inject_globals()` provides global template variables used across templates (not just index).
  - Session-dependent UI: `cube_positioner_enabled` checks `'admin_id' in session` (line ~3018 in inject_globals) — impossible to know at build time.
  - Dynamic data: projects/blog/testimonials come from DB; content can change via admin.
  - Routes beyond `/`: many are dynamic (blog posts, admin, client operations) and require Flask.

**Verdict:** Current Vercel config does *not* support independent frontend delivery. To do A2 safely you cannot just “copy index.html” as-is — you must split: either pre-render with appropriate fallbacks, or move only statically-cacheable portions to Vercel and keep all dynamic/interactive parts calling Render APIs. But note: existing public forms POST to Flask endpoints (e.g. `/contact`, `/start-a-project`, `/subscribe`, `/partner`) with CSRF protection; moving frontend breaks same-origin assumptions unless CORS + CSRF handled carefully. Also session cookies need same-site/domain alignment.

## 7. Recommended Architecture

**Recommendation: A1 (Keep Flask on Render, optimize).** Do not split frontend to Vercel purely to mask Render cold start. The smallest safe fix is to eliminate/defer blocking work on the homepage render and ensure resilience, while keeping existing design, routes, admin, forms, DB, and auth intact.

**Limitations of A1:**
- If Render remains on free tier, cold start still occurs on first request after idle (even if HTML generation is instant, process must spin up). The `keep-warm.yml` (every 5 min) mitigates this for the health endpoint and will keep instance awake if it runs; however GitHub Actions scheduled jobs can have delays and Render’s idle timeout (comment says ~15 min).
- Cannot guarantee zero cold start without paid tier (always-on).
- Some homepage data still requires DB availability at render time (or cached values).

**When A2 might be justified:** Only if cold start is unacceptable for business reasons and keep-warm is insufficient, *and* you accept the cost/complexity/risk of splitting. Even then, A2 is not necessary to “load while Render is asleep” for the HTML — you can’t generate Flask-rendered HTML without Flask running. A static shell on Vercel loads immediately but any dynamic content shown on initial view must come from APIs (which still require Render awake unless cached at CDN with staleness).
